## Render adaptation: proposed, not yet implemented

Use two services in the same region (Oregon is used by existing account web
services):

- A **private Blender service** running the pinned LinuxServer image. Mount a
  persistent disk at `/config`. Do not publish its unauthenticated desktop.
  Keep one instance: one desktop and one disk, no horizontal scaling.
- A **public gateway web service**, built from `gateway/Dockerfile` with build
  context `gateway`. Set `UPSTREAM` to the private service's internal HTTP
  origin on port 3000. Set `PUBLIC_ORIGIN` to the actual HTTPS gateway origin
  with no trailing slash. Configure LOGIN_USER, PASSWORD_HASH and SESSION_KEY
  as private runtime settings using the formats generated by configure.py.

Render terminates TLS, so omit Caddy on Render. Change gateway's hardcoded
8080 port to `int(os.environ.get("PORT", "8080"))`. The public service must
bind 0.0.0.0 and its assigned PORT. Confirm the actual private hostname and port
from Render; do not assume Compose's `blender` DNS name works there.

For the private service, use a tiny Dockerfile FROM the pinned Blender image
and COPY `scripts/smoke_blender.py` into `/opt/workstation-checks/`. Retain the
upstream entrypoint; it initializes the desktop. Translate the Blender env
settings in compose.yaml into runtime environment variables. The `/config`
disk must be writable by UID/GID 1000.

**Feasibility gates before committing to Render:**

- Verify LinuxServer's desktop starts under Render's container restrictions.
  It may need shared memory or system capabilities that Render does not expose.
  Compose's `shm_size: 1gb` is not automatically transferable. Inspect actual
  `/dev/shm`, startup logs and memory usage; do not assume compatibility.
- Use the JPEG encoder/X11 fallback; our cloud browser had no WebGPU adapter.
  Server software OpenGL must still work. CPU-only rendering is the initial
  scope, with no GPU acceleration promise.
- Confirm WebSocket upgrade and binary transport work through Render's HTTPS
  proxy and our gateway. Check all desktop endpoints, not just the HTML shell.
- Determine current plan resources/pricing in the dashboard. An initial test
  target is 4–8 GB RAM for Blender; this is an untested sizing assumption.
  Include gateway, disk and outbound streaming bandwidth costs. Static-site
  hosting or object storage alone cannot run this native desktop.
- If native desktop startup requires unsupported privileges or shared memory,
  stop investing in Render and use a normal Linux VM with the supplied Compose
  stack. Explain the observed failure; don't fake a successful deployment.

## Verification and security review

The proxy tests exercise authentication, cross-origin rejection, session
expiry, binary/text WebSockets, gzip responses, uploads and header filtering.
Review compressed request handling, redirects, WebSocket headers, upload size
limits, malformed login bodies and rate limiting under concurrent requests.
The current implementation is a prototype, not a completed security audit.
Do not remove authentication to make a health check pass.

Run the native smoke script in the Blender container with:

```sh
blender --background --factory-startup --threads 2 --python-exit-code 9 --python /opt/workstation-checks/smoke_blender.py
```

It writes a unique directory under `/config/workstation-checks`, checks PNG and
GLB signatures and reopens the saved scene. On a VM, `verify_host.py` wraps
this; on Render, run the command using the service shell/SSH. Do not install
Docker inside Render just to run the Compose verification wrapper.

Then use the **actual target cloud browser**: sign in securely, open Blender,
move a cube, orbit the viewport, render, save under `/config`, reload, reopen
and confirm the edit. Restart the service and verify the saved file survives.
Test file upload/download. Record screenshots and observed latency, rather
than inventing FPS. The smoke script deliberately reports
`browser_control_tested: false`; only real browser interaction can establish it.

This is a publicly reachable, authenticated **single trusted workstation**.
An authenticated desktop user can execute code in its container. Anonymous
public access, multi-user isolation, quotas and abuse prevention are separate
future work. Never describe it as safe public free compute for everyone.

# AstraBlender

Co-created by Dakota Rain Lock and GPT Astra.

An independent access layer for the real Blender desktop. Blender itself is
created by the Blender Foundation and its contributors. This project does not
claim to invent browser desktop streaming or reimplement Blender.

## Original implementation status — 8 September 2026

Deployment candidate, **not yet a running public service**. The authentication
proxy, Docker Compose configuration and native Blender verification scripts
are implemented. Python syntax can be checked locally. Integration tests are
provided but have not passed here: dependency installation was interrupted by
a network approval cancellation. Docker and Blender are absent from this
workspace. No server has been purchased or provisioned.

The intended path is browser → HTTPS/Caddy → authenticated proxy → Selkies →
native Blender. JPEG desktop streaming avoids requiring WebGPU on the client.
Actual browser input, rendering, save/reopen and connection stability still
need verification on the deployed host. Never interpret the proxy health
endpoint as proof that Blender works.

## Deploy

Use a Linux x86-64 server with Docker Engine and Docker Compose v2 installed.
An initial evaluation target is 4 vCPU, 8 GB RAM and 40 GB disk; this is an
untested sizing assumption, not a performance guarantee. CPU rendering is the
initial configuration. Large scenes may require much more memory or a GPU.

1. Copy this directory to the server. Configure a DNS hostname pointing to it.
2. Allow inbound TCP 80 and 443. Restrict SSH to your administration address.
   Do not expose ports 3000, 3001 or 8080.
3. Run `python3 scripts/configure.py --domain blender.example.com` using your
   actual hostname. It securely prompts for a password and creates `.env`
   without printing the credentials. Keep that file private.
4. Run `docker compose config --quiet`, then `docker compose up -d --build`.
5. Visit the HTTPS hostname and sign in. For an agent, use its supported secure
   browser sign-in flow; do not paste your password into a chat message.
6. Run `python3 scripts/verify_host.py`. It creates a tiny scene, renders PNG,
   exports GLB, saves and reopens a `.blend`, and records actual results and
   image digests in `deploy-lock.json`.
7. In the browser, move the cube, save under `/config`, reload the page, reopen
   the file and confirm the edit. Restart the containers and repeat to test
   persistence. Record failures; do not mark the deployment complete without
   this browser test.

## Operations and limits

This is one trusted workstation, not anonymous public compute or isolated
multi-user hosting. An authenticated user controls a desktop and can execute
code in its container. Only share access with trusted operators. Authentication
is a prototype requiring review before production use. Sessions last eight
hours. Rotating SESSION_KEY and restarting the gateway revokes all sessions;
there is no individual-session revocation UI.

Save projects under `/config`; its named Docker volume survives ordinary
container replacement. Back up that volume off-host. `docker compose down`
stops services while retaining named volumes; **do not use `down -v`**, which
deletes the data. A stopped cloud VM may still incur charges; provider billing
and backup retention must be checked separately.

Blender's image release is pinned to `5.2.1-ls238`; Caddy and Python base images
are floating. Capture deployed digests with the verification script and review
updates before applying them. No uptime, frame-rate or cost claims are made.
